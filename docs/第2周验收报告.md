## 一、Day 8~9：Java 四模块接口

### 标准动作（每个模块一致，方便前端统一封装）

| 修改 | `PUT /plan/{id}` | `PUT /plan/task/{id}` | `PUT /wrong-question/{id}` | `PUT /notice/{id}/read` |

| 导出 | — | — | `GET /wrong-question/export` | — |

### 分页与条件查询

- 统一 `PageQuery` 基类，`pageNum/pageSize` 在**一处**收敛（`maxLimit=500`），
  而不是散落在每个 Service 里各写一遍边界判断。
- 条件查询用 `LambdaQueryWrapper` 动态拼接：`eq(条件, 字段, 值)` 形式，
  条件为 false 时该段不拼进 SQL，天然避免 `where 1=1` 和各种 if 分支。
- 排序字段走**白名单分支**（`createTime` / `difficulty` / `mastery` / `id`），
  不把前端字符串拼进 `order by`。

### 错题本额外做的

- 按科目 / 掌握度 / 题型 / 难度 / 标签 / 关键字 / 时间范围筛选
- 标签筛选：`GROUP BY ... HAVING COUNT(DISTINCT name) = n` 做多标签**交集**，一次查询
- 批量删除、批量标记掌握度（越权 ID 静默过滤，返回实际生效条数）
- EasyExcel 导出：单次上限 10000 条，文件名按 RFC 5987 编码（中文名不乱码）

### 学习计划额外做的

- 创建计划时按 `target_date` + `daily_minutes` + 科目**均摊生成** `plan_task`
- 生成器抽成 `PlanTaskGenerator` 接口：本周是「均摊版」，第 3 周换成
  「LangGraph Agent 版」只替换实现类，上层流程不动
- 上限保护：跨度超过 400 天直接拒绝并提示，而不是悄悄截断生成半截计划
- 修改计划**不重新生成任务**，避免把用户已勾选的任务冲掉

### 进度模块

- 完成 `plan_task` 时写 `study_record`，形成「勾选 → 记录 → 统计」闭环
- 统计 SQL 直接 `group by`（`StudyRecordMapper`），走 `idx_user_date` 索引
- 一个聚合接口返回概览卡片 + 4 张图数据：
  `dailyMinutes`（时长折线）、`completionTrend`（完成率折线）、
  `subjectDistribution`（科目饼图）、`masteryDistribution`（掌握度柱状）

### 通知模块

- 列表（**未读优先**再按时间倒序）、未读数（角标）、单条/批量/全部已读、删除
- `push()` 先定义好，第 4 周的 RocketMQ 消费者直接调它，接口层不用改

## 三、本周修复的两个真实缺陷

这两个都是**编译通过、启动成功、只有真跑接口才暴露**的问题，很值得写进踩坑记录。

### 1. 启动即失败的 Bean 循环依赖

```
APPLICATION FAILED TO START
The dependencies of some of the beans in the application context form a cycle:
   progressController → progressServiceImpl
   ↓
|  planTaskServiceImpl → studyPlanServiceImpl
└─┘
```

**原因**：`StudyPlanServiceImpl` 需要 `PlanTaskService` 批量落任务，
而 `PlanTaskServiceImpl` 又需要 `StudyPlanService` 校验计划归属。两个 Bean 互相依赖。

**处理**：刻意**不**用 `spring.main.allow-circular-references=true` 掩盖。
校验计划归属只需要一次按主键查询，`PlanTaskServiceImpl` 改注入 `StudyPlanMapper`，
循环从设计上消除。这样依赖方向是单向的：任务 → 计划（Mapper 层），计划 → 任务（Service 层）。

### 2. Excel 导出运行时 ClassNotFound

```
ExcelGenerateException: java.lang.NoClassDefFoundError:
    org/apache/commons/compress/archivers/zip/ZipArchiveOutputStream
```

**原因**：pom 里为了让依赖干净，把 `commons-compress` 从 EasyExcel 里排除掉了。
EasyExcel 依赖 `poi-ooxml` 写 `.xlsx`，而 poi-ooxml 的 XSSF 写盘正是走
`commons-compress` 的 `ZipArchiveOutputStream`。

**为什么难发现**：编译期不报错（代码里没有直接引用它）、启动也不报错
（只有真正写 xlsx 才加载这个类），只有点了"导出"才炸。

**处理**：移除排除，并显式声明 `commons-compress:1.26.2`。
**经验**：排除传递依赖是"看不见的契约破坏"，尤其是 `commons-*` / `jackson-*`
这类被大量框架间接使用的库；排除后必须把相关功能都点一遍。

## 四、一个环境层面的发现

验收过程中 **Redis 意外停止**，导致登录接口返回
`code=500 服务器内部错误`（根因是 `PoolException: Could not get a resource from the pool`
→ `Connection refused: 127.0.0.1:6379`）。

**这不是代码缺陷**（refresh token 必须落 Redis，这是设计的一部分），但暴露了两件事：

1. **启动顺序有依赖**：Java 服务依赖 Redis 才能完成登录。
   `scripts/start-all.bat` 已按 MySQL → Redis → RocketMQ → 后端 的顺序拉起，
   但**已有一个正在运行的服务时 Redis 挂掉**不会自愈。
2. **运维提示可以更友好**：当前 Redis 不可用时用户看到的是"服务器内部错误"。
   第 4 周做 Redis 缓存加固时，建议把"基础设施不可用"与"业务异常"区分开，
   返回 `code=5001 服务暂时不可用（缓存异常），请稍后重试` 并让网关/监控告警。

> 已把这条写进本报告的遗留问题，并在第 4 周任务里落实。
