## 四、本周修复的两个真实缺陷

### 1. 问答消息"双写竞态"：每条 assistant 消息存了两份

**现象**：压测时发现 `chat_message` 里每条 assistant 消息都有两条完全相同
（同会话、同一秒、内容一致），只有"中途断连"那条是单份。

**排查**：

- Java 透传结束时（finally）保存 assistant；Python 在发 `[DONE]` **之前**也会调
  `/internal/chat/messages` 保存一遍；
- 顺序上 Python 的调用先到（Java 那时还在读流），Java 的保存后到、
  且没有幂等守卫 → 每轮必双写；
- 内部接口里的"同 session 同 role 同内容不重复插"**赢不了时序**：
  两边都在对方插入之前完成了存在性检查（典型 TOCTOU）。

**修复**：**写入口唯一化** —— SSE 链路落库由 Java 独占（user 在开流前写、
assistant 在流后写，连接中断也能保存部分内容），Python 不再参与写库；
内部接口保留为"幂等补写入口"并在 javadoc/注释里写清适用边界。
同时清理了历史重复行，并把会话 `message_count` 重算为实际行数
（此前两个写入方各自 "+N"，计数同样对不上账）。

### 2. 长计划生成超时：72 天计划"AI 没有生成任何任务"

**现象**：`POST /plan/agent-generate`（考研、目标 2026-12-20、72 天）连续 3 次
尝试全部失败，日志为 `OpenAITimeoutError('Request timed out.')`，
最终返回"模型没有返回可解析的 JSON 计划"。

**排查**：

- **单次要模型输出 72 天的完整 JSON**（约 15K~30K 字符 + 思考模式的思维链），
  远超 `ChatOpenAI` 的 60 秒超时（`timeout=60, max_retries=2` → 每次"尝试"
  实为 3×60s 全超时）；
- 模型偶尔输出"看起来像 JSON、实际解析失败"的文本（长度 3.9K~5.8K），
  触发**整段计划重新生成**（8 个分片全部重跑），代价 2 分钟以上。

**修复（三层）**：

1. **分片并发生成**：按 10 天切段、`ThreadPoolExecutor` 8 路并发，
   每段超时 120s → 单次输出降到 2K~4K 字符，72 天计划总耗时压到分钟级；
2. **`response_format={"type": "json_object"}`** 约束模型只输出 JSON 对象
   （DashScope OpenAI 兼容协议支持），从根上减少解析失败；
3. **确定性修正**取代重试：每日时长超限（削减任务时长）/ 任务条数超限（移除多余条目）
   由代码毫秒级修好并记入 warnings，不再触发整段重生成；
   单个分片解析失败则**分片级原地重试一次**（比整段重跑便宜得多）。

修复后实测：72 天计划 **67 秒首轮通过**（修复前 385 秒 / 3 轮重试仍失败告终），
覆盖全部 72 天、每日任务时长 ≤ 120 分钟；Java 侧端到端（smoke F）
落库 101 条任务 / 72 天 / 自检重试 0 次。
