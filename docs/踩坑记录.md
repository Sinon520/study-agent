## 1. LangChain 会静默丢弃 `reasoning_content`（第 1~2 周实测，影响第 3 周设计）

**现象**

用 `langchain_openai.ChatOpenAI` 调 `qwen3.7-flash`（思考模型），
响应里**完全看不到思维链**：

- 非流式：`AIMessage.additional_kwargs` 只有 `{'refusal': None}`；
- 流式：`AIMessageChunk.additional_kwargs` **全程为空**。

但用**原生 openai SDK** 调同一个模型、同一句 prompt，`message.reasoning_content`
有 667~1043 字符的思维链；流式下 `delta.reasoning_content` 会先逐块下发，
`delta.content` 要到最后才出现（实测 90 个 chunk：首个 reasoning 在 +0.42s，
首个 content 在 +3.66s）。

**根因**

`langchain_openai.chat_models.base` 里的两个**模块级**转换函数
`_convert_delta_to_message_chunk`（流式）与 `_convert_dict_to_message`（非流式）
只映射 OpenAI 标准字段，没有映射 `reasoning_content`，于是被静默丢掉。

唯一残留的痕迹是 usage 里的
`completion_tokens_details.reasoning_tokens`（实测 190/181）——
**说明思考确实发生了，只是文本没了**。

**解决（两条路，都实测通过）**

1. **猴补丁**：替换上述两个模块级函数，把 `reasoning_content` 注入
   `additional_kwargs`（因为调用点按全局名解析，替换模块属性即可同时拦截流式与非流式）。
   写成了 `enable_reasoning_passthrough()`，启动时由 `PRESERVE_REASONING=true` 自动安装，
   幂等且失败不影响服务启动。
2. **直接用原生 SDK**（推荐给 SSE）：`AsyncOpenAI` 的
   `delta.reasoning_content` 与 `delta.content` 天然分离，不需要任何补丁。

**经验**

- **框架的"字段裁剪"是最危险的一类 bug**：不报错、不告警，只是数据凭空消失。
  接入任何 LLM 网关/包装层后，都要**拿原生 SDK 对一遍字段**。
- 判断"思考是否发生"不能只看文本，`usage` 里的 token 统计是可靠旁证。
- 第 3 周 SSE 直接用原生 `AsyncOpenAI`，别在 LangChain 上继续加补丁。

## 2. HuggingFace 镜像下载"挂死"：不是慢，是卡住（第 1~2 周）

**现象**

`bge-m3` 的 `pytorch_model.bin`（2165.9 MB）下载到 227 MB 后，
连续 60 秒采样**零字节增长**，日志永久停在 `[ 9/15] pytorch_model.bin`，
连 `HF_HUB_DOWNLOAD_TIMEOUT=120` 都没触发 —— socket 不关，也不给数据。

**根因**

镜像返回的 302 签名地址带 `X-Amz-Expires=3600`（1 小时有效），
而本机到镜像的实际速率只有约 0.1~0.2 MB/s。
**2.2GB 的单文件必然超过一次 URL 的生命周期**，于是续传成为唯一可行路径；
而"卡住"是因为连接既不超时也不报错。

**解决**

给下载脚本加**看门狗**：零增长超过阈值（180s）就杀掉子进程并重新续传，
最多重启 50 次。实测有效：

```
[WATCHDOG] 检测到停滞：已 30s 无字节增长（当前缓存 227.1 MB）-> 杀掉子进程并续传
[WATCHDOG] 子进程退出码 1，5 秒后第 2 次重启 ...
```

另外默认**跳过 `onnx/` 目录**（`onnx/model.onnx_data` 是 2161.6 MB 的重复权重），
省一半带宽。

**经验**

- 大文件下载必须有"看门狗 + 断点续传"，不能只靠超时。
  **超时机制在"连接活着但不给数据"时是无效的。**
- `HF_HUB_OFFLINE=1` 是个陷阱：`bge-m3` 的 `imgs/.DS_Store` 在镜像上恒 403，
  snapshot 永远不"完整"，离线模式下 transformers 做完整性校验会抛
  `IncompleteSnapshotError`，**即使权重已经下好了**。改用"按文件预检"更可靠。

## 3. hf-xet 绕过镜像直连，报 401（第 1~2 周）

**现象**

```
File reconstruction error: CAS Client Error 401 Unauthorized,
domain: https://cas-server.xethub.hf.co/...
```

**根因**

`hf-xet` 传输后端会**绕过 `HF_ENDPOINT` 镜像**，直连 HuggingFace 的 CAS 服务；
未登录时直接 401。

**解决**

```python
os.environ.setdefault("HF_HUB_DISABLE_XET", "1")   # 退回经典 HTTP 传输
```

配合 `HF_ENDPOINT=https://hf-mirror.com` 生效。

**经验**

设了镜像不等于全部流量都走镜像 —— 某些新传输后端有自己的域名和鉴权，
要单独关掉。遇到"明明配了镜像还连官方域名"的报错，先查这个包。

## 4. 模型"就绪预检"把 724KB 的 onnx 当成有效权重（第 1~2 周）

**现象**

模型没下完，但预检判定"已就绪"，于是请求内真的去加载模型，
第一次 `POST /debug/embed` 花了 **20.3 秒**才返回 503。

**根因**

权重候选文件里包含了 `onnx/model.onnx`（仅 724KB）——
它只是个占位/导出文件，不是真正的权重。预检看到它就认为模型可用。

**解决**

- 权重候选**只认** `model.safetensors` / `pytorch_model.bin`；
- 必需文件再加上 `tokenizer.json`；
- 新增 `app/services/model_cache.py` 做**请求前预检**，
  并开启 `MODEL_LOCAL_FILES_ONLY=true`：模型缺失时**立刻** 503，
  绝不在请求里联网下几 GB。

修正后同样的请求 **0.013 秒**返回 503。

**经验**

"就绪检查"必须针对**真正的必需文件**，而不是"目录里有没有文件"。
一个错误的预检比没有预检更糟：它把"快速失败"变成了"慢速失败"。

## 5. emoji + GBK 控制台会直接杀掉 Python 重试循环（第 1~2 周）

**现象**

下载脚本偶发整体退出，栈里是
`UnicodeEncodeError: 'gbk' codec can't encode character '\u274c'`。

**根因**

Windows 控制台默认 GBK。脚本用 `print("❌ ...")` 输出状态，
**打印这一步抛异常**，而它正好在重试循环里 —— 于是重试机制自己被一个 emoji 打断了。

**解决**

```python
sys.stdout.reconfigure(encoding="utf-8", errors="replace", line_buffering=True)
```

并且状态标记只用 ASCII（`[OK]` / `[FAIL]`）。
顺带 `line_buffering=True` 解决了"日志经 `Tee-Object` 重定向后进度要等缓冲满才落盘"的问题。

**经验**

后台常驻脚本的**日志代码本身不能抛异常**。
所有 `print` 都当成"可能失败的外部调用"来对待，或者统一走一个不会抛的日志函数。

## 7. PowerShell 写文件把中文注释写成乱码，导致 `mvn compile` 失败（第 1 周）

**现象**

```
错误: 编码 UTF-8 的不可映射字符 (0xB4)
```

javac 报某个 `.java` 文件不是合法 UTF-8，打开一看中文注释全是 `寰俊灏忕▼搴?` 这样的乱码。

**根因**

我用了一条 PowerShell 命令去改文件的 `package` 声明：

```powershell
(Get-Content $f -Raw).Replace(...) | Set-Content -NoNewline $f
```

这条命令跑在了 **Windows PowerShell 5.1 宿主**上（不是 PowerShell 7），`Set-Content` 在 5.1 里的默认编码是 **ANSI（中文系统即 GBK/936）**。源文件本来是 UTF-8，被按 GBK 写回去之后，中文注释的字节全部损坏，而且损坏后的字节序列**也**不是合法 UTF-8，`javac -encoding UTF-8` 直接拒绝编译。

关键点：`Get-Content -Raw` 在 5.1 里按 ANSI 读 UTF-8 文件时不会报错，只是静默地把中文变成乱码字符串 —— **读和写各错一次，最终结果不可逆**。

**解决**

1. 用 UTF-8 重写该文件（改用编辑工具，不走 PowerShell 管道）。
2. 加一道扫描，确认 `com.studyagent` 下所有 `.java` 都是合法 UTF-8：

```powershell
Get-ChildItem -Recurse -File .\src\main\java\com\studyagent -Filter *.java | ForEach-Object {
  $b = [System.IO.File]::ReadAllBytes($_.FullName)
  try { $u = New-Object System.Text.UTF8Encoding($false, $true); [void]$u.GetString($b) }
  catch { "BAD: $($_.FullName)" }
}
```

**经验**

- 中文注释的项目里，**不要**用 `Set-Content` / `Out-File` 不加 `-Encoding`；要么显式 `-Encoding utf8`，要么用编辑工具而不是文本管道。
- PowerShell 里 `pwsh -Command` 不保证落到 7.x 宿主，脚本里判断版本或用 `[System.IO.File]::WriteAllText($path, $text, [System.Text.UTF8Encoding]::new($false))` 才稳。
- 这类问题在 CI 上会表现为"我本地能编译"，所以在工程里加一个编码自检脚本（或 Git 的 `.gitattributes` 声明）比靠人记要可靠。

## 8. RocketMQ Broker 把内网 IP 注册到 NameServer，客户端连不上（第 0 周）

**现象**

Broker 进程起来了，`mqadmin clusterList` 能看到 broker，但 `#Addr` 显示的是 `192.168.1.23:10911` 而不是 `127.0.0.1:10911`。多网卡机器上客户端可能路由到不可达的地址。

**根因**

`mqbroker.cmd -n 127.0.0.1:9876` 里的 `-n` 只指定了 **NameServer 地址**，Broker 自己对外注册的地址由 `brokerIP1` 决定，不配置时取第一块可用网卡的内网 IP。

**解决**

新建 `conf/broker-local.conf`，显式写死本地回环：

```
namesrvAddr = 127.0.0.1:9876
brokerIP1 = 127.0.0.1
listenPort = 10911
autoCreateTopicEnable = true
autoCreateSubscriptionGroup = true
brokerRole = ASYNC_MASTER
flushDiskType = ASYNC_FLUSH
```

启动改为 `mqbroker.cmd -c conf\broker-local.conf -n 127.0.0.1:9876`。

**经验**

单机开发环境里，任何"注册自己地址给别的组件"的中间件都要显式指定回环地址：RocketMQ 的 `brokerIP1`、Nacos 的 `ip`、Eureka 的 `prefer-ip-address` 都是同一类问题。

## 9. 本机 RocketMQ 开启了 ACL，producer/consumer 直接被拒（第 1 周发现，第 4 周处理）

**现象**

普通客户端发消息时报：

```
RemotingException ... CODE: 1  DESC: check client ip or username failed
```

**根因**

本机这套 RocketMQ 的 `conf/plain_acl.yml` 里 `globalWhiteRemoteAddresses` 没有覆盖 `127.0.0.1`，即 ACL 生效但没有给本地客户端放行。

**处理**

第 1 周只需要依赖与配置项，所以**刻意不写任何消费者**，避免服务启动失败。第 4 周接入前二选一：

- 方案 A（省事）：`broker-local.conf` 加 `aclEnable=false` 并重启 Broker；
- 方案 B（更真实）：保留 ACL，在 Java 侧配 `rocketmq.producer.access-key` / `secret-key`，并给本地 IP 加白名单。

**经验**

把"基础设施的隐性限制"当作**跨周待办**写进验收报告的遗留问题表，而不是等踩到时再临时处理——这类问题一旦在演示前一小时爆出来就是灾难。

## 10. jjwt 0.12.x 的 API 与 0.11.x 完全不兼容（第 1 周）

**现象**

按老写法 `Jwts.parser().setSigningKey(key).parseClaimsJws(token)` 编译不过。

**根因**

jjwt 0.12.x 做了破坏性重构：解析器改成 builder 模式，密钥必须用 `SecretKey`，`Claims` 的取用方式也变了。

**解决**

```java
// 签发
Jwts.builder().subject(...).claim(...).signWith(secretKey).compact();

// 解析
Jwts.parser().verifyWith(secretKey).requireIssuer(issuer)
    .build().parseSignedClaims(token).getPayload();
```

密钥必须用 `Keys.hmacShaKeyFor(secret.getBytes(UTF_8))`，**并且 HS256 要求密钥至少 256 bit（32 字节）**，否则抛 `WeakKeyException`。所以我在 `JwtTokenProvider` 构造器里主动校验长度并给出明确报错，而不是等到运行时才炸。

**经验**

涉及安全库的版本升级，先看官方 migration guide 再写代码；同时在**构造阶段**做前置校验（fail fast），比运行时报错好排查得多。

## 11. Spring Boot 3 必须用 `mybatis-plus-spring-boot3-starter`（第 1 周）

**现象**

引入 `mybatis-plus-boot-starter` 后启动报 `NoClassDefFoundError` / 自动配置不生效。

**根因**

MyBatis-Plus 从 3.5.4 起拆出了 Spring Boot 3 专用 starter，因为 Boot 3 用 Jakarta EE 9+（`jakarta.*`），旧的 starter 依赖 `javax.*`。

**解决**

```xml
<dependency>
    <groupId>com.baomidou</groupId>
    <artifactId>mybatis-plus-spring-boot3-starter</artifactId>
    <version>3.5.7</version>
</dependency>
```

**经验**

Boot 3 生态里 `javax` → `jakarta` 的迁移会波及所有 starter，选依赖时先确认 artifact 名里有没有 `boot3`。

## 12. `spring-boot-starter-parent` 与自定义 `finalName` 的冲突（第 1 周）

**现象**

想让产物叫 `server-java-1.0.0-SNAPSHOT.jar`，但用了 `spring-boot-starter-parent` 后产物名不受控。

**解决**

不继承 parent，改为 `dependencyManagement` 里 `import` `spring-boot-dependencies` BOM，这样版本管理照样有，`<finalName>` 完全可控。同时要手动配 `spring-boot-maven-plugin` 的 `repackage`。

**代价**

失去 parent 提供的默认插件配置（编译插件的 `annotationProcessorPaths` 等），需要显式声明——尤其是 **Lombok 在 Boot 3 + JDK 21 下必须显式配 `annotationProcessorPaths`**，否则注解处理器不生效，编译报"找不到 getter/setter"。

## 13. Spring Boot 2.6+ 禁止 Bean 循环依赖：两个 Service 互相注入（第 2 周）

**现象**

```
APPLICATION FAILED TO START
The dependencies of some of the beans in the application context form a cycle:
   progressController → progressServiceImpl
       ↓
|  planTaskServiceImpl → studyPlanServiceImpl
└─┘
```

**根因**

- `StudyPlanServiceImpl` 创建计划后要批量落 `plan_task` → 依赖 `PlanTaskService`；
- `PlanTaskServiceImpl` 新增任务时要校验"这个计划是不是你的" → 依赖 `StudyPlanService`。

两个 Service 互相注入，Spring Boot 2.6 起默认禁止循环引用（`allow-circular-references` 默认 false）。

**解决**

**刻意没有**打开 `spring.main.allow-circular-references=true`——那只是把设计问题掩盖成运行时隐患。

真正的修法：`PlanTaskServiceImpl` 里校验计划归属**只需要一次按主键查询**，
所以改注入 `StudyPlanMapper`（数据访问层），依赖方向立刻变成单向：

```
PlanTaskService ──> StudyPlanMapper          （任务 → 计划，Mapper 层）
StudyPlanService ──> PlanTaskService          （计划 → 任务，Service 层）
```

**经验**

出现循环依赖时，先问一句"我需要的到底是对方的**能力**还是**数据**"。
只要一次查询能解决，就应该下沉到 Mapper，而不是在两个 Service 之间拉一根反向线。
（同理：如果确实需要对方的复合能力，就抽第三个 Service 或发领域事件，也别开那个开关。）

## 15. 排除 `commons-compress` 让 Excel 导出在运行时炸（第 2 周）

**现象**

编译通过、启动正常、Swagger 能打开，一点"导出 Excel"就返回
`{"code":500,"msg":"服务器内部错误"}`。日志里：

```
com.alibaba.excel.exception.ExcelGenerateException:
    java.lang.NoClassDefFoundError:
    org/apache/commons/compress/archivers/zip/ZipArchiveOutputStream
```

**根因**

为了让依赖树干净，pom 里把 `commons-compress` 从 EasyExcel 里排除掉了。
但 EasyExcel 依赖 `poi-ooxml` 写 `.xlsx`，而 poi-ooxml 的 XSSF 写盘正是走
`commons-compress` 的 `ZipArchiveOutputStream`。

**为什么极难发现**

- 编译期不报错（我们代码里没有直接引用这个类）；
- 启动不报错（只有真正写 xlsx 时才加载）；
- 只有点了导出，或者跑了集成测试，才会炸。

**解决**

移除该 `<exclusion>`，并显式声明 `org.apache.commons:commons-compress:1.26.2`。

**经验**

排除传递依赖是**看不见的契约破坏**，尤其 `commons-*` / `jackson-*` / `slf4j-*`
这类被大量框架间接使用的库。排除后必须把相关功能**都点一遍**；
更稳的做法是：只排除明确知道没人用的东西，或者在 CI 里加一条"导出接口冒烟测试"。

## 16. pnpm 10+ 不跑 postinstall，导致 `pnpm run` 报出一个指向错误位置的失败（第 2 周）

**现象**

```
$ pnpm run build:mp-weixin
[ERR_PNPM_IGNORED_BUILDS] Ignored build scripts: core-js@3.50.0, esbuild@0.20.1
Run "pnpm approve-builds" to pick which dependencies should be allowed to run scripts.
[ERROR] Command failed with exit code 1: ... pnpm install
pnpm: Command failed with exit code 1: ... pnpm install
    at runDepsStatusCheck (...)
```

**三个坑叠在一起**

1. **pnpm 10+ 默认不执行依赖的 postinstall**（供应链安全策略）。
   `esbuild` / `core-js` 的 postinstall 被拦下 → `pnpm install` 以
   `ERR_PNPM_IGNORED_BUILDS` + exit 1 结束。
2. **`pnpm run` 之前会跑一次 `depsStatusCheck`**：它发现"有被忽略的构建脚本"，
   就自动重跑 `install`，而那次 install 同样 exit 1 —— 于是 `build` 脚本
   **还没执行到 uni/vite 就失败了**，报错信息却指向 `pnpm install`，
   完全看不出真正原因。
3. **pnpm 11 起不再读取 `package.json` 里的 `"pnpm"` 字段**。
   我按老写法加了 `"pnpm": { "onlyBuiltDependencies": [...] }`，
   只得到一句 `The "pnpm" field in package.json is no longer read by pnpm` 的警告，
   配置**静默失效**。

**解决**

```bash
pnpm approve-builds --all
```

它会生成 `pnpm-workspace.yaml`：

```yaml
allowBuilds:
  core-js: true
  esbuild: true
```

**经验**

- 报"某个 install/其他命令失败"时，先确认**失败的是不是真正想跑的那条命令**。
  这里的 `Command failed ... pnpm install` 是 pnpm 自己触发的，不是我们的脚本。
- 包管理器的安全策略变更（pnpm 10 的 postinstall、pnpm 11 的配置迁移）会以
  "静默忽略配置 + 莫名其妙的失败"的形式出现，先查版本对应文档再看代码。
