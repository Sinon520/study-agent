## 四、第 4 周的关键设计与修复（面试可直接讲）

1. **MQ 三链路的统一纪律**：
   - traceId 跨进程并发两段：HTTP 头之外，**序列化进 MQ 消息体**，消费端重入 MDC
     （含 `@Scheduled` 触发的消息，由调度线程生成并随消息传递）；
   - **幂等三件套**：报告落库=唯一键 upsert；站内通知=(userId,type,bizId) 查重；
     微信推送=仅在"首次建通知"时发（重投不重复触达）；
   - **失败语义分级**：可重试（网络/5xx/非终态错误码）抛异常走 MQ 重试；
     终态（未授权/额度不足/无 openid/微信 43101 等）记 `skipped` 放行 ——
     否则死信队列会被"用户不愿意收"的噪音淹没；
   - 效果实证：一次 LLM 外部中断的消费消息，依赖恢复后由重试自动补上。

2. **复盘报告**：统计聚合复用进度页口径（数字与用户所见一致）；
   `@Scheduled` 只负责"投递"，生成与触发解耦；同周期唯一键 upsert，
   重触发只刷新不产新行；站内通知与微信推送按节流规则联动。

3. **微信订阅消息的额度模型**：微信语义是"一次订阅=一次发送额度"——
   服务端建 `wx_subscribe` 记账（同意 +1 上限 20、拒绝不回收存量、原子扣减防超发）；
   调度期先按授权过滤，只给"能收到的人"投递；`access_token` 缓存 Redis +
   `SETNX` 锁防并发重复刷新（TTL 提前 5 分钟）；每次尝试落 `wx_push_log` 可审计。

4. **Cache Aside 的三个纪律**（`common/cache/RedisCacheHelper`）：
   缓存不接管可用性（Redis 异常按 miss 降级）；**写库后删缓存且选在事务提交后**
   （先删会"删完又被并发读回填旧值"）；坏值自愈（反序列化失败删 key 回源）。
   计划详情的 key **含 userId** —— 命中即等于归属校验通过，
   越权请求必然 miss → 403（缓存不会把越权防护绕过去）。

5. **并发事故复盘（踩坑 #25）**：FastAPI `async def` 端点里跑阻塞 LLM 调用，
   把事件循环占死 —— 6 个用户周报串行 4.5 分钟且全服务无响应。
   修复为同步 `def`（线程池执行），方法论固化成并发探针脚本（3 路 60s 全完成）。
